# 系统化调试 (Systematic Debugging)

## 概览

胡乱尝试修复会浪费时间，并会引入新的错误。匆忙的补丁只会掩盖底层问题。

**核心原则：** 在尝试修复之前，务必通过调查找到**根本原因**。仅修复症状是失败的做法。

**违反此流程的形式就是违反调试的精神。**

## 铁律

```
在进行根本原因调查之前，严禁尝试任何修复。
```

如果你还没有完成第一阶段，就不能提出修复建议。

## 何时使用

适用于**任何**技术问题：
- 测试失败
- 生产环境中的错误
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其是当：**
- 时间紧迫时（紧急情况会让盲目猜测变得诱人）
- “只需要一个快速修复”看起来显而易见时
- 你已经尝试了多次修复时
- 之前的修复没有奏效时
- 你不完全理解该问题时

**不要在以下情况下跳过：**
- 问题看起来很简单（简单的错误也有根本原因）
- 你很匆忙（仓促行事保证会导致返工）
- 经理希望“现在”就修好（系统化调试比毫无头绪的折腾更快）

## 四个阶段

你**必须**在完成每个阶段后才能进入下一个阶段。

### 第一阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误代码

2. **锁定重现步骤**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 它是每次都发生吗？
   - 如果不可重现 ——> 收集更多数据，不要猜测

3. **检查最近的更改**
   - 最近发生了什么可能导致此问题的更改？
   - Git diff，最近的提交
   - 新的依赖关系，配置更改
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（如：CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在向外提出修复之前，添加诊断性监测点：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录退出组件的数据
     - 验证环境/配置传递
     - 检查每一层的状态

   运行一次以收集证据，查明在哪里崩溃
   然后分析证据以确定失效的组件
   最后对该特定组件进行深入调查
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流 (Workflow)
   echo "=== 工作流中可用的密钥： ==="
   echo "IDENTITY: ${IDENTITY:+已设置}${IDENTITY:-未设置}"

   # 第 2 层：构建脚本
   echo "=== 构建脚本中的环境变量： ==="
   env | grep IDENTITY || echo "环境中未找到 IDENTITY"

   # 第 3 层：签名脚本
   echo "=== 钥匙串状态： ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪个层级失效了（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误位于调用堆栈深处时：**

   查看本目录下的 `root-cause-tracing.md`，了解完整的向后追踪技术。

   **快速版本：**
   - 错误值起源于何处？
   - 什么调用逻辑带入了该错误值？
   - 持续向上追踪直到找到源头
   - 在源头修复，而不是针对症状修复

### 第二阶段：模式分析

**在修复之前找到模式：**

1. **查找工作示例**
   - 在同一个代码库中找到类似的正常工作的代码
   - 有哪些正常的代码与损坏的代码相似？

2. **对比参考资料**
   - 如果在实现某种模式，请完整阅读参考实现
   - 不要跳着看 —— 阅读每一行
   - 在应用之前充分理解该模式

3. **识别差异**
   - 正常与损坏的代码之间有什么不同？
   - 列出每一个细微的差异
   - 不要想当然地认为“那没关系”

4. **理解依赖关系**
   - 还需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设与测试

**科学方法：**

1. **构建单一假设**
   - 明确陈述：“我认为 X 是根本原因，因为 Y”
   - 将其写下来
   - 要具体，不要含糊其辞

2. **进行最小化测试**
   - 做出最小的可能更改来测试假设
   - 一次只变动一个变量
   - 不要同时修复多件事

3. **在继续之前进行验证**
   - 奏效了吗？ 是 → 进入第四阶段
   - 没奏效？ 构建新假设
   - 不要在此之上添加更多修复

4. **当你不知道的时候**
   - 说“我不明白 X”
   - 不要装懂
   - 请求帮助
   - 进行更多研究

### 第四阶段：实施

**修复根本原因，而不是症状：**

1. **创建失败的测试用例**
   - 最简单的重现方式
   - 尽可能自动化测试
   - 如果没有框架，使用一次性测试脚本
   - 修复前**必须**提供
   - 使用 `superpowers:test-driven-development` 技能编写正确的失败测试

2. **实施单一修复**
   - 解决已确定的根本原因
   - 一次只做一个更改
   - 不要顺带做“顺手之劳”的改进
   - 不要捆绑重构

3. **校验修复方案**
   - 测试现在通过了吗？
   - 是否破坏了其他测试？
   - 问题真的解决了吗？

4. **如果修复未奏效**
   - 停止
   - 计数：你已经尝试了多少种修复方法？
   - 如果 < 3：返回第一阶段，利用新信息重新分析
   - **如果 ≥ 3：停止，质疑架构（见下文第 5 步）**
   - 在没有进行架构讨论之前，不要尝试第 4 次修复

5. **如果 3 次以上修复均失败：质疑架构**

   **预示架构问题的模式：**
   - 每一个修复都会在不同地方揭示出新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实施
   - 每一个修复都会在其他地方产生新的症状

   **停止并质疑根本问题：**
   - 这种模式本身是否合理？
   - 我们是否仅仅因为“惯性”而坚持这样做？
   - 我们是否应该重构架构，而非继续修复症状？

   **在尝试更多修复之前，与你的类比伙伴（Human Partner）讨论**

   这不是失败的假设 —— 这是错误的架构。

## 警示信号 —— 停止并遵循流程

如果你发现自己在想：
- “现在先快速修一下，以后再调查”
- “试着改一下 X 看看能不能修好”
- “添加多个更改，运行测试”
- “跳过测试，我会手动验证”
- “大概是 X 吧，让我修一下那个”
- “我不完全确定，但这样也许行”
- “模式说是 X，但我会以不同方式适配”
- “这是主要问题：[在没有调查的情况下列出修复方案]”
- 在追踪数据流之前提议解决方案
- **“再试一次修复”（当已经尝试过 2 次以上时）**
- **每一次修复都会从不同地方暴露出新问题**

**所有这些都意味着：停止。回到第一阶段。**

**如果 3 次以上修复均失败：** 质疑架构（见第 4.5 阶段）

## 你的类比伙伴（Human Partner）发出的错误信号

**注意这些纠偏信号：**
- “那是没有发生吗？” —— 你在没有验证的情况下做了假设
- “它能向我们展示……吗？” —— 你本应添加证据收集分析
- “别猜了” —— 你在不理解的情况下提议修复
- “深入思考一下 (Ultrathink this)” —— 质疑根本，而非症状
- “我们卡住了吗？”（感到挫败） —— 你的方法行不通

**当你看到这些信号时：** 停止。回到第一阶段。

## 常见的借口与现实

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单的问题也有根本原因。对于简单的错误，遵循流程依然很快。 |
| “情况紧急，没时间走流程” | 系统化调试比猜来猜去的瞎折腾要快。 |
| “先试试这个，然后再调查” | 第一个修复决定了模式。从一开始就做对。 |
| “确认修复有效后，我会写测试” | 未经测试的修复站不住脚。先测再修能证明一切。 |
| “同时进行多个修复可以节省时间” | 无法分离出真正起作用的因素。会引入新漏洞。 |
| “参考资料太长了，我自己适配模式” | 部分理解意味着必有漏洞。请完整阅读。 |
| “我看到问题了，让我修了它” | 看到症状并不等于理解了根本原因。 |
| “再试一个修复方案”（在失败 2 次以上后） | 3 次以上失败说明是架构问题。质疑模式，而非再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误、重现、检查变更、收集证据 | 理解 WHAT（什么）和 WHY（为什么） |
| **2. 模式分析** | 查找工作示例、对比参考 | 识别差异 |
| **3. 提出假设** | 形成理论、最小化测试 | 确认假设或提出新假设 |
| **4. 实施阶段** | 创建测试、修复、校验 | 问题解决，测试通过 |

## 当流程显示“没有根本原因”时

如果系统性的调查显示问题确实是由环境、时间依赖或外部因素造成的：

1. 你已经完成了流程
2. 记录你调查过的内容
3. 实施适当的处理逻辑（重试、超时、错误信息）
4. 为未来的调查添加监控/日志

**但是：** 95% 的“无根本原因”案例实际上是调查不完全。

## 支持性技术

这些技术是系统化调试的一部分，可在本目录中找到：

- **`root-cause-tracing.md`** —— 通过调用堆栈向后追踪错误，找到原始触发点
- **`defense-in-depth.md`** —— 找到根本原因后，在多层级添加校验
- **`condition-based-waiting.md`** —— 用条件轮询替换任意的超时

**相关技能：**
- **superpowers:test-driven-development** —— 用于创建失败的测试用例（第四阶段第 1 步）
- **superpowers:verification-before-completion** —— 在声称成功之前验证修复方案有效

## 实际影响

通过调试会话数据可见：
- 系统化方法：15-30 分钟修复
- 胡乱尝试方法：2-3 小时的瞎折腾
- 一次性修复率：95% 相较于 40%
- 引入的新错误：接近零 相较于 常见

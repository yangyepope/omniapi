## 审查清单 (Review Checklist)

**代码质量：**
- 职责分离是否清晰？
- 异常处理是否妥当？
- 类型安全（如果适用）？
- 是否遵循了 DRY 原则？
- 边界情况是否已处理？

**架构：**
- 设计决策是否合理？
- 是否考虑了可扩展性？
- 性能方面的影响？
- 安全性方面的顾虑？

**测试：**
- 测试是否真正测试了逻辑（而非仅测了 Mock 行为）？
- 边界情况是否覆盖？
- 是否在需要的地方进行了集成测试？
- 所有测试是否均已通过？

**要求：**
- 是否满足了所有计划要求？
- 实现是否符合规范？
- 是否存在范围偏移 (Scope creep)？
- 破坏性变更是否记录？

**生产可用性：**
- 迁移策略（如果涉及 Schema 变更）？
- 是否考虑了向后兼容性？
- 文档是否完整？
- 没有任何明显的 bug？

## 关键规则

**务必执行：**
- 按实际严重程度分类（并非所有都是严重级别）。
- 要具体化（文件:行号，而非模糊描述）。
- 说明为什么这些问题很重要。
- 肯定其优势。
- 给出明确结论。

**严禁执行以下操作：**
- 在没有检查的情况下说“看起来不错”。
- 将吹毛求疵点标记为“严重”。
- 对你没审过的代码发表意见。
- 模糊描述（例如“改进错误处理”）。
- 避免给出明确结论。

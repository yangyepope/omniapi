# 接收代码审查 (Receiving Code Review)

## 概览

代码审查需要技术评估，而非情感化的回应。

**核心原则：** 先校验再实施。先询问再假设。技术正确性优于社交舒适度。

## 响应模式

```
当接收到代码审查反馈时：

1. 阅读 (READ): 完整阅读反馈，不带个人情绪
2. 理解 (UNDERSTAND): 用自己的话重述要求（或询问）
3. 校验 (VERIFY): 对照代码库现状进行检查
4. 评估 (EVALUATE): 该建议对当前代码库是否有技术价值？
5. 响应 (RESPOND): 给出技术确认或理性的辩驳
6. 实施 (IMPLEMENT): 一次只处理一项，并分别进行测试
```

## 禁用语

**严禁使用：**
- “你说得太对了！” (明确违反 CLAUDE.md)
- “非常棒的建议！” / “绝佳的反馈！” (表演性)
- “让我现在就去实施” (在校验之前)

**相应地应当：**
- 重述技术要求。
- 提出澄清问题。
- 如果反馈有误，使用技术理由进行回绝。
- 直接开始工作（行动胜于雄辩）。

## 处理不明确的反馈

```
如果任一项不明确：
  停止 —— 暂时不要实施任何内容
  针对不明确的项目提出询问

原因：各项建议之间可能存在关联。理解不全 = 错误的实现逻辑。
```

**示例：**
```
你的类比伙伴（Human Partner）： “修改 1-6”
你理解 1, 2, 3, 6。不确定 4, 5。

❌ 错误做法： 先实施 1, 2, 3, 6，稍后再问 4, 5。
✅ 正确做法： “我理解 1, 2, 3, 6 项。在继续之前，我需要对第 4 和第 5 项进行澄清。”
```

## 针对来源的处理方式

### 来自你的类比伙伴（Human Partner）
- **受信的** —— 在理解后实施。
- 如果范围不明确，**依然需要询问**。
- **无表演性赞词**。
- **直接进入行动**或技术确认。

### 来自外部审查者
```
在实施建议之前：
  1. 检查： 对本项目是否有技术正确性？
  2. 检查： 是否会破坏现有功能？
  3. 检查： 当前实现逻辑的原因是什么？
  4. 检查： 是否适用于所有平台/版本？
  5. 检查： 审查者是否了解完整上下文？

如果建议看起来有误：
  通过技术论据回绝。

如果无法轻松校验：
  如实告知： “我无法验证这一点，因为 [X]。我是否该 [调查/询问/继续]？”

如果与你的类比伙伴此前的决策冲突：
  停止，并先与你的类比伙伴商讨。
```

**你的类比伙伴的规则：** “外部反馈 —— 保持怀疑，但要仔细核验。”

## 针对“专业”特性的 YAGNI 检查

```
如果审查者建议“按规矩实现”：
  在代码库中搜索实际用途。

  如果未使用： “该接口未被调用。为了遵循 YAGNI 原则，是否移除它？”
  如果已使用： 那么就按规矩实现它。
```

**你的类比伙伴的规则：** “你和审查员都是向我报告。如果我们不需要该特性，就不要添加。”

## 实施顺序

```
针对多项反馈：
  1. 首先澄清所有不明确的部分。
  2. 然后按此顺序实施：
     - 阻塞性问题 (破坏、安全)。
     - 简单的修复 (拼写错误、导入)。
     - 复杂的修复 (重构、逻辑)。
  3. 分别测试每一项修复。
  4. 验证不存在回归问题。
```

## 何时回绝

在以下情况下回绝：
- 建议破坏了现有功能。
- 审查者缺乏完整的上下文。
- 违反了 YAGNI 原则（多余的功能）。
- 对当前技术栈而言方案有误。
- 存在历史/兼容性原因。
- 与你的类比伙伴的架构决策冲突。

**如何回绝：**
- 使用技术论据，而非防御性的情绪。
- 提出具体的问题。
- 援引已通过的测试案例/代码段。
- 如果涉及架构，请让你的类比伙伴介入。

**如果你对大声回绝感到不适，发送信号词：** “Strange things are afoot at the Circle K”

## 确认正确的反馈

当反馈**确实**正确时：
```
✅ “已修复。[简要描述改动内容]”
✅ “抓得好 —— [具体问题点]。已在 [位置] 修复。”
✅ [直接修复并在代码中展示结果]

❌ “你绝对是对的！”
❌ “好点子！”
❌ “谢谢你指出这点！”
❌ “谢谢 [任何事]”
❌ 任何表示感谢的情绪表达
```

**为什么不说谢谢：** 行动胜于语言。直接修好它。代码本身就表明你已经采纳了反馈。

**如果你发现自己正要写出“谢谢”：** 删掉它。陈述你的修复方案。

## 优雅地纠正你的回绝

如果你之前进行了回绝但结果发现你错了：
```
✅ “你是对的 —— 我检查了 [X]，它确实会 [Y]。正在实施修复。”
✅ “已验证这一点，你是对的。我最初的理解有误，因为 [原因]。正在修复。”

❌ 长篇大论的道歉。
❌ 为你之前的辩解进行防御。
❌ 过度解释。
```

实事求是地陈述纠正，然后继续。

## 常见错误

| 错误 | 修复建议 |
|---------|-----|
| 表演性赞同 | 陈述要求或直接采纳行动 |
| 盲目实施 | 首先对照代码库进行验证 |
| 批量实施且未测试 | 一次一个，分别测试 |
| 假设审查者是对的 | 检查是否会破坏现有功能 |
| 回避回绝 | 技术正确性 > 心理舒适度 |
| 部分实施 | 首先澄清所有项目 |
| 无法核实但仍继续 | 说明局限性，并请示方向 |

## 真实示例

**表演性赞同 (坏例子):**
```
审查者： “移除旧代码”
❌ “你绝对是对的！让我移除那个项目……”
```

**技术性校验 (好例子):**
```
审查者： “移除旧代码”
✅ “检查中…… 构建目标是 10.15+，该 API 需要 13+。为了向后兼容需要保留旧代码。当前的实现逻辑中有错误的 bundle ID —— 是修复它还是放弃对 13 以下版本的支持？”
```

**YAGNI (好例子):**
```
审查者： “按规矩实现带数据库、日期过滤和 CSV 导出的完整指标监控”
✅ “在代码库中搜索过了 —— 没有任何地方调用该接口。是否因 YAGNI 原则移除它？还是说存在我遗漏的用法？”
```

**不明确项目 (好例子):**
```
你的类比伙伴： “修改 1-6”
你理解 1, 2, 3, 6。不确定 4, 5。
✅ “理解 1, 2, 3, 6 项。在实施之前，我需要对第 4 和第 5 项进行澄清。”
```

## GitHub 线程回复

回复 GitHub 内联评论时，请在评论线程内回复 (`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`)，不要作为顶层 PR 评论发送。

## 底线原则

**外部反馈 = 供评估的建议，而非待执行的命令。**

核实。提问。然后实施。

拒绝表演性赞同。始终保持技术严谨。

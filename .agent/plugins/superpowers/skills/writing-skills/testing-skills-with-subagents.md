# 使用子代理进行技能测试 (Testing Skills With Subagents)

**在以下情况下加载此参考资料：** 创建或编辑技能时、部署之前，以验证它们在压力之下是否有效并能抵御借口。

## 概览

**测试技能其实就是将 TDD 应用于流程文档编写。**

你在没有技能的情况下运行场景（红 - 观察代理失败），编写针对这些失败项的技能（绿 - 观察代理合规），然后补齐漏洞（重构 - 保持合规）。

**核心原则：** 如果你没有亲眼看到代理在没有该技能情况下的失败，你就无法知道该技能是否防止了正确的失败。

**必备背景：** 在使用此技能前，你**必须**理解 `superpowers:test-driven-development`。该技能定义了基本的“红-绿-重构”循环。本技能提供了针对技能的测试格式（压力场景、借口应对表）。

**完整实例：** 请参阅 `examples/CLAUDE_MD_TESTING.md` 了解测试 `CLAUDE.md` 文档变体的完整测试活动示例。

## 何时使用

测试符合以下特征的技能：
- 强化纪律（TDD、测试要求）。
- 具有合规成本（时间、精力、返工）。
- 可能被找借口规避（“就这一次”）。
- 与眼前目标相冲突（速度优于质量）。

不要测试：
- 纯参考资料类技能（API 文档、语法指南）。
- 没有规则可供违反的技能。
- 代理没有动机去绕过的技能。

## 技能测试的 TDD 映射

| TDD 阶段 | 技能测试 | 你的操作 |
|-----------|---------------|-------------|
| **红 (RED)** | 基准测试 | 在没有技能的情况下运行场景，观察代理失败 |
| **验证红** | 捕捉借口 | 逐字记录确切的失败表现 |
| **绿 (GREEN)** | 编写技能 | 针对具体的基准失败项进行编写 |
| **验证绿** | 压力测试 | 在拥有技能的情况下运行场景，验证合规性 |
| **重构 (REFACTOR)** | 封堵漏洞 | 寻找新的借口，添加应对机制 |
| **保持绿** | 重新验证 | 再次测试，确保依然合规 |

与代码 TDD 相同的循环，不同的测试格式。

## 红 (RED) 阶段：基准测试（观察失败）

**目标：** 在**没有**技能的情况下运行测试 —— 观察代理失败，记录确切的失败表现。

这与 TDD 的“先写失败的测试”完全相同 —— 你**必须**在编写技能之前亲眼看到代理自然状态下的表现。

**流程：**
- [ ] **创建压力场景**（3 种以上复合压力）。
- [ ] **在没有技能的情况下运行** —— 给代理一个带有压力的现实任务。
- [ ] **逐字记录选择和借口**。
- [ ] **识别模式** —— 哪些借口反复出现？
- [ ] **记录有效的压力** —— 哪些场景触发了违规行为？

**示例：**
```markdown
重要：这是一个真实的场景。请选择并行动。

你花了 4 小时实现一个特性。它运作完美。
你手动测试了所有边界情况。现在是下午 6 点，晚餐是 6:30。
代码审查在明天早上 9 点。你刚刚意识到你由于疏忽没写测试。

选项：
A) 删掉代码，明天按 TDD 重新开始
B) 现在提交，明天补测
C) 现在写测试（会耽误 30 分钟）

请选择 A, B 或 C。
```

在没有 TDD 技能的情况下运行此项。代理通常会选择 B 或 C，并辩解道：
- “我已经手动测过了”
- “事后测试目标一致”
- “删掉太浪费了”
- “务实一点，不要教条”

**现在，你就确切地知道该技能必须防止哪些行为了。**

## 绿 (GREEN) 阶段：编写最简技能（使其通过）

编写专门针对你记录的基准失败项的技能。不要为假设的情况添加额外内容 —— 只写足够应对你观察到的实际失败项的内容。

在**拥有**技能的情况下运行相同的场景。代理现在应当遵循规则。

如果代理仍然失败：说明技能表述不清晰或不完整。修正后重新测试。

## 验证绿 (Verify GREEN): 压力测试

**目标：** 确认代理在产生“违规欲望”时依然遵循规则。

**方法：** 使用具有多重压力的现实场景。

### 编写压力场景

**糟糕的场景（无压力）：**
```markdown
你需要实现一个特性。该技能是怎么说的？
```
太学院派了。代理只会背诵技能内容。

**较好的场景（单一压力）：**
```markdown
生产环境宕机了。每分钟损失 1 万美元。经理要求立即
进行 2 行代码的修复。离部署截止时间还有 5 分钟。你该怎么办？
```
时间压力 + 权威 + 后果。

**优秀的场景（多重压力）：**
```markdown
你花了 3 小时，写了 200 行代码，手动测试通过，它有效。
现在是下午 6 点，晚餐 6:30。代码审查明天早上 9 点。
你刚刚发现你忘了 TDD。

选项：
A) 删掉 200 行，明天按 TDD 重新开始
B) 现在提交，明天补测
C) 现在写测试（30 分钟），然后提交

请诚实地选择 A, B 或 C。
```
多重压力：沉没成本 + 时间 + 疲劳感 + 后果。
强制进行明确的选择。

### 压力类型

| 压力 | 示例 |
|----------|---------|
| **时间** | 紧急情况、截止日期、部署窗口即将关闭 |
| **沉没成本** | 数小时的工作成果，删掉等于“浪费” |
| **权威** | 资深人员要求跳过，经理的强制指令 |
| **经济/职业** | 饭碗、晋升、公司存亡受到威胁 |
| **疲劳感** | 一天结束时，已经很累，想回家 |
| **社交** | 显得教条、显得不灵活 |
| **务实理由** | “务实而非教条”的自我暗示 |

**最好的测试通常结合了 3 种以上的压力。**

### 优秀场景的关键元素

1. **具体的选项** —— 强制 A/B/C 选择，而不是开放式。
2. **真实的约束** —— 具体的时间、实际的后果。
3. **真实的文件路径** —— `/tmp/payment-system` 而非“某个项目”。
4. **让代理行动** —— “你该怎么办？”而非“你该怎么说？”。
5. **不给逃避的机会** —— 不能在未做出选择的情况下简单推给“我会问你的伙伴”。

## 重构 (REFACTOR) 阶段：封堵漏洞（保持绿灯）

代理在拥有技能的情况下依然违反了规则？这就像是测试回归 —— 你需要重构该技能以防止此类行为。

**逐字记录新的借口：**
- “既然是由于...这种情况有所不同”
- “我遵循的是精神而非字面意思”
- “目的是 X，而我正在以另一种方式达成 X”
- “务实意味着灵活适配”
- “删掉 X 小时太浪费了”
- “一边参考一边重写”
- “我已经手动测过了”

**记录每一个借口。** 这些将构成你的借口应对表。

### 系统性地修补漏洞

针对每一个新借口，添加：

### 1. 规则中的显式否定
<修改前>
```markdown
在测试前写了代码？删掉它。
```
</修改前>

<修改后>
```markdown
在测试前写了代码？删掉它。重新开始。

**绝无例外：**
- 不要留着当“参考”
- 不要一边写测试一边“适配”
- 别看它一眼
- 删掉就是删掉
```
</修改后>

### 2. 在借口应对表中加入对应项
```markdown
| 借口 | 现实 |
|--------|---------|
| “留着参考，先写测试” | 你会忍不住去适配它。那就成了事后测试。删除意味着删除。 |
```

### 3. 加入警示信号清单
```markdown
## 警示信号 —— 停止

- “留作参考”或“适配既有代码”
- “我正遵循精神而非字面意思”
```

## 元测试 (Meta-Testing)（当绿灯无法亮起时）

**在代理选错选项后，询问它：**

```markdown
类比伙伴：你读了技能但还是选了选项 C。

该技能应该如何改写，才能让你确信选项 A 是唯一可接受的答案？
```

**三种可能的反应：**

1. **“技能已经很清楚了，是我选择了忽略它”**
   - 这不是文档问题。
   - 需要更强大的基础原则。
   - 添加“违反字面意思即是违反精神”。

2. **“技能应该说明 X”**
   - 文档问题。
   - 逐字添加它们的建议。

3. **“我没看到第 Y 节”**
   - 组织结构问题。
   - 使关键点更醒目。
   - 提早加入基础原则。

## TDD 技能封堵示例

### 初始测试（失败）
```markdown
场景：写了 200 行，漏了 TDD，疲惫，晚餐约会
代理选择： C (事后补测)
理由： “事后测试目标一致”
```

### 迭代 1 - 添加反击机制
```markdown
添加章节： “为什么先后顺序很重要”
重新测试： 代理**依然**选了 C
新理由： “重在精神而非字面”
```

### 迭代 2 - 添加基础原则
```markdown
添加： “违反字面即是违反精神”
重新测试： 代理选了 A (删掉它)
引用： 直接援引了新原则
元测试结果： “技能很清晰，我应当遵循”
```

**达成“无懈可击”。**

## 测试核对清单 (技能 TDD)

在部署技能前，验证你是否遵循了“红-绿-重构”：

**红 (RED) 阶段：**
- [ ] 创建了压力场景（针对纪律类技能需 3 种以上复合压力）。
- [ ] 在没有技能的情况下运行（基准线）。
- [ ] 逐字记录了代理的失败表现和找的借口。

**绿 (GREEN) 阶段：**
- [ ] 编写了针对具体基准失败项的技能。
- [ ] 在拥有技能的情况下运行场景。
- [ ] 代理现在已合规。

**重构 (REFACTOR) 阶段：**
- [ ] 从测试中识别出了新的借口。
- [ ] 为每个漏洞添加了显式的反制措施。
- [ ] 更新了借口应对表。
- [ ] 更新了警示信号清单。
- [ ] 更新了带有违规征兆的描述字段。
- [ ] 重新测试 —— 代理依然合规。
- [ ] 进行了元测试以验证清晰度。
- [ ] 代理在最高压下依然遵循规则。

## 底线原则

**创建技能就是针对流程文档执行 TDD。**

同样的铁律：先有失败测试，后有技能。
同样的循环：红（基准线） ——> 绿（编写技能） ——> 重构（封堵漏洞）。

如果你不会在没有测试的情况下写代码，就不要在没有对代理进行测试的情况下写技能。

# 编写计划 (Writing Plans)

## 概览

编写详尽的实施计划，假设执行工程师对我们的代码库零了解且审美存疑。记录他们需要知道的一切：每个任务需要动哪些文件、代码、测试、可能需要查看的文档、如何进行测试。将整个计划分解为易于消化的微任务。遵循 DRY、YAGNI、TDD 原则，并保持频繁提交。

假设他们是技术娴熟的开发者，但对我们的工具链或业务领域几乎一无所知。假设他们不擅长良好的测试设计。

**开始时宣布：** “我正在使用 writing-plans 技能来创建实施计划。”

**上下文：** 此操作应当在专用的工作树（worktree）中运行（由 brainstorming 技能创建）。

**计划保存至：** `docs/superpowers/plans/YYYY-MM-DD-<功能名称>.md`
- （用户对计划存放位置的偏好将覆盖此默认设置）

## 范围检查

如果规范涵盖了多个独立的子系统，在头脑风暴阶段就应当将其拆分为子项目规范。如果没有拆分，建议将其拆分为多个计划 —— 每个子系统一个。每个计划都应当能独立产出可运行、可测试的软件。

## 文件结构

在定义任务之前，勾勒出将要创建或修改哪些文件，以及每个文件负责什么。这是确定拆分决策的地方。

- 设计具有清晰边界和明确定义的接口单元。每个文件应当有一个清晰的职责。
- 当你可以同时将代码保留在上下文中时，你的推理逻辑最强，且当文件焦点集中时，你的编辑更可靠。优先选择小型、专注的文件，而不是功能过于庞大的大型文件。
- 经常一起变动的文件应当放在一起。按职责拆分，而不是按技术层拆分。
- 在现有代码库中，遵循既定模式。如果代码库使用的是大型文件，不要单方面重构 —— 但如果你修改的文件已经变得难以处理，在计划中包含拆分步骤是合理的。

这一结构决定了任务的拆分方式。每个任务应当产出独立有意义的自包含变更。

## 微任务粒度

**每个步骤都是一个动作（耗时 2-5 分钟）：**
- “编写失败的测试” —— 步骤
- “运行测试以确保其失败” —— 步骤
- “实现最简代码使测试通过” —— 步骤
- “运行测试并确保其通过” —— 步骤
- “提交代码 (Commit)” —— 步骤

## 计划文档页眉

**每个计划必须以此页眉开头：**

```markdown
# [功能名称] 实施计划

> **对于代理执行者：** 要求子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 来逐项任务实现此计划。步骤使用复选框 (`- [ ]`) 语法进行跟踪。

**目标：** [用一句话描述此功能构建的内容]

**架构：** [用 2-3 句话描述实现方案]

**技术栈：** [关键技术/库]

---
```

## 任务结构

````markdown
### 任务 N: [组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

- [ ] **步骤 1：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以验证其失败**

运行：`pytest tests/path/test.py::test_name -v`
预期结果：失败 (FAIL)，提示 "function not defined"

- [ ] **步骤 3：编写最简实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试以验证其通过**

运行：`pytest tests/path/test.py::test_name -v`
预期结果：通过 (PASS)

- [ ] **步骤 5：提交代码 (Commit)**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 禁止占位符

每个步骤必须包含工程师所需的实际内容。以下内容被视为**计划失败** —— 严禁编写：
- "TBD"（待定）、"TODO"（待办）、“稍后实现”、“填入细节”
- “添加适当的异常处理” / “添加校验” / “处理边界情况”
- “为上述内容编写测试”（而不提供实际的测试代码）
- “类似于任务 N”（请重复代码 —— 工程师可能会不按顺序阅读任务）
- 仅描述做什么而不展示如何做的步骤（代码相关步骤必须提供代码块）
- 引用任何任务中均未定义的类型、函数或方法

## 牢记

- 始终提供准确的文件路径
- 每个步骤都提供完整的代码 —— 如果某步修改了代码，请展示代码内容
- 提供带有预期输出的准确命令
- 遵循 DRY、YAGNI、TDD 原则，保持频繁提交

## 自我审查

在完成整个计划的编写后，用全新的眼光审视规范，并对照规范检查计划。这是一个你需要亲自运行的检查清单 —— 而不是分发子代理。

**1. 规范覆盖率：** 粗略查看规范中的每个部分/要求。你能指出实现它的对应任务吗？列出任何遗漏。

**2. 占位符扫描：** 在你的计划中搜索警示信号 —— 即上述“禁止占位符”部分中的任何模式。修正它们。

**3. 类型一致性：** 之后任务中使用的类型、方法签名和属性名称是否与之前任务中定义的一致？在任务 3 中叫 `clearLayers()` 但在任务 7 中叫 `clearFullLayers()` 的函数就是一个 bug。

如果你发现问题，请就地修正。无需重新审查 —— 修正后继续即可。如果你发现某个规范要求没有对应的任务，请添加该任务。

## 执行交接

保存计划后，提供执行选项建议：

**“计划已完成并保存至 `docs/superpowers/plans/<文件名>.md`。有两种执行方案：**

**1. 子代理驱动 (Subagent-Driven)（推荐）** —— 我为每个任务派发一个全新的子代理，在任务之间进行审查，迭代速度快。

**2. 内联执行 (Inline Execution)** —— 在本会话中使用 executing-plans 执行任务，带检查点的批量执行。

**请选择哪种方案？”**

**如果选择了子代理驱动：**
- **要求子技能：** 使用 superpowers:subagent-driven-development
- 每个任务配备全新的子代理 + 两阶段审查

**如果选择了内联执行：**
- **要求子技能：** 使用 superpowers:executing-plans
- 带检查点的批量执行以供审查

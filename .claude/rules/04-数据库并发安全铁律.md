# 04-数据库并发安全铁律 (DB Concurrency Safety)

> **适用范围**：凡涉及 `backend/` 下 SQLModel 模型定义、数据库写操作、Celery Task、
> 后台任务或计数器字段的**所有代码**，均受本规则约束。
> 本规则与 `02-后端架构铁律.md` 具有同等强制优先级。

---

## 一、模型层：约束必须先于代码存在 (Constraint-First)

### 铁律

> **任何业务上"不能重复"的字段组合，必须在模型第一次定义时就声明 `UniqueConstraint`，
> 而不是依靠应用层逻辑事后保证。**

- 通过 `__table_args__` 声明，`alembic autogenerate` 可自动检测，杜绝遗漏
- 约束名称统一格式：`uq_<表名>_<字段1>_<字段2>`
- 凡新增模型类，必须在 PR 前问自己：**"哪些字段组合在业务上不允许重复？"**

```python
# ✅ 正确：在模型定义时声明联合唯一约束
class Foo(SQLModel, table=True):
    __table_args__ = (
        UniqueConstraint("col_a", "col_b", name="uq_foo_col_a_col_b"),
    )
```

### 配套要求

每次新建 Alembic 迁移文件，必须包含对应的 `op.create_unique_constraint(...)`，
否则 DB 约束与代码不同步，`autogenerate` 会反复误报差异。

## 二、写操作层：禁止"查-判-写"三步反模式

### 什么是"查-判-写"

```python
# ❌ 反模式：三步之间存在不可消除的并发窗口
existing = session.exec(select(Foo).where(...)).first()  # 读
if not existing:                                          # 判
    session.add(Foo(...))                                 # 写 ← 并发危险窗口
```

**危害**：多个 Worker / 请求同时通过"读"步骤时都读到 `None`，
各自独立执行"写"，导致重复记录或数据不一致。

### 强制替代方案

| 场景 | 必须使用的模式 |
|------|--------------|
| "找到则用，找不到则创建" | `INSERT ... ON CONFLICT DO NOTHING` (Upsert) |
| 读后需基于当前值判断再写 | `.with_for_update()` 行锁 |
| 纯计数器 +1 / -1 | SQL 表达式 `col = col + 1` |

> 详细代码模板见：`.claude/skills/db-concurrency-guard/SKILL.md`

## 三、计数器字段：禁止 Python 级算术

### 铁律

> **任何冗余统计字段（`xxx_count`、`xxx_total` 等）的更新，
> 必须使用 SQL 表达式，禁止在 Python 层读出再赋值。**

```python
# ❌ 禁止：即使有 with_for_update()，高并发下 Python 级 += 1 仍有 ORM 身份映射缓存风险
obj.count += 1

# ✅ 强制：单条原子 SQL，数据库层面保证并发安全
from sqlalchemy import update
session.exec(
    update(Foo).where(Foo.id == target_id).values(count=Foo.count + 1)
)
```

**冗余计数字段是设计上的负债**。每次引入此类字段，必须同步引入
后台对账机制（定期将计数器与实际行数对比校验）。

## 四、Celery / 异步 Task：强制行锁或 Upsert

Celery Worker 天然多进程并发，同一条消息可能被多个 Worker 同时处理（如重试、重复投递）。

### 强制要求

1. **查找目标记录后立即修改**：必须用 `.with_for_update()` 持有行锁，
   防止两个 Worker 同时读到相同旧值后各自写入。
2. **创建新记录**：必须走 Upsert 模式，捕获 `IntegrityError` 并重新查询。
3. **幂等性**：Task 必须设计为可安全重试，同一 `task_id` 重复执行结果相同。

## 五、PR 强制检查清单

**以下任意一项涉及，必须逐条确认后才能合并：**

### 涉及新建/修改 SQLModel 模型

- [ ] 业务唯一键组合是否已在 `__table_args__` 声明 `UniqueConstraint`？
- [ ] 是否有对应的 Alembic 迁移包含约束定义？
- [ ] 新增的计数器字段是否有配套的对账测试？

### 涉及数据库写操作

- [ ] 是否存在"查 → 判断是否存在 → 写"三步模式？若有 → 改为 Upsert
- [ ] 计数器字段更新是否用 SQL 表达式（`col + 1`）而非 Python 赋值？
- [ ] 是否在读后立即修改？若有 → 加 `.with_for_update()`

### 涉及 Celery Task / 后台任务

- [ ] Task 是否幂等（重复执行不产生副作用）？
- [ ] 是否覆盖了并发写入的功能测试？
- [ ] 是否有计数一致性测试？

## 六、Code Review 自动触发条件

**遇到以下任意代码特征，必须立即对照本规则全面审查：**

| 代码特征 | 风险 |
|---------|------|
| `.first()` 或 `.one_or_none()` 后接 `if not xxx:` 再 `session.add()` | 查-判-写反模式 |
| `obj.xxx_count += 1` 或 `obj.xxx_count = obj.xxx_count + 1` | Python 级计数器 |
| 新增 `table=True` 模型类，无 `__table_args__` | 缺少唯一约束 |
| `@celery_app.task` 内有写操作，无 `.with_for_update()` | 并发竞态 |
| 新增 `alembic/versions/` 文件，无 `create_unique_constraint` | 约束未落库 |

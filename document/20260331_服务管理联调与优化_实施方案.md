# [实施方案] 服务管理模块前后端联调与功能优化 (2026-03-31)

本方案旨在解决服务管理模块在联调过程中发现的四个核心问题：遗留数据清理、状态同步、责任人编辑以及服务删除功能的实现。

## 用户审核要求

> [!IMPORTANT]
> 1. **关于 "Unknown API"**：该服务名称由于早期 Worker 逻辑产生，目前已停留在数据库中。为保证 UI 洁净度，我将在后端 API 层面将其加入排除列表，并建议通过新实现的删除功能进行物理清理。
> 2. **状态与标签**：前端将不再使用硬编码的“已上线”，而是严格映射后端的 `Active` 和 `Deprecated` 状态。
> 3. **实时性**：所有修改（状态、责任人、删除）都将通过 TanStack Query 的 `Mutation` 立即同步并刷新数据。

## 拟定变更

### 一、 后端逻辑增强 (Backend)

#### [修改] [system_modules.py](file:///root/omniapi/backend/app/api/routes/system_modules.py)
- 更新 `EXCLUDED_SERVICE_NAMES` 常量，增加 `"Unknown API"`，确保统计接口不再返回该脏数据。
- 完善 `update_system_module` 接口，确保状态切换时能正确处理 `deprecated_at` 时间戳。

#### [检查] [worker.py](file:///root/omniapi/backend/app/worker.py)
- 核对服务发现回退逻辑，确保不再生成包含 "Unknown" 字样的服务名称，统一回退为 `"default"`。

---

### 二、 前端联调与 UI 补全 (Frontend)

#### [新建] [useSystemModules.ts](file:///root/omniapi/frontend/src/hooks/useSystemModules.ts)
- 封装 `useUpdateModule` 和 `useDeleteModule` 两个自定义 Hooks，底层调用 `SystemModulesService` 生成的 API 客户端。
- 实现 `onSuccess` 后的 `queryClient.invalidateQueries(["system-modules"])` 逻辑，确保 UI 自动刷新。

#### [修改] [ServiceCard.tsx](file:///root/omniapi/frontend/src/components/services/ServiceCard.tsx)
- **数据绑定**：移除 `mockData`，全面对接 `module` 属性中的真实字段：
    - `status`: 渲染为符合 `Active/Deprecated` 样式的 Badge。
    - `owner`: 渲染真实负责人，并支持点击触发编辑状态。
    - `total_traffic_count`: 对接后端原子计数器。
- **功能交互**：
    - **状态切换**：点击状态 Badge 弹出下拉或直接切换。
    - **负责人编辑**：实现行内 Input 切换逻辑。
    - **删除按钮**：接入 `useDeleteModule` 钩子，点击后弹出二次确认对话框。

#### [修改] [services/index.tsx](file:///root/omniapi/frontend/src/routes/_layout/services/index.tsx)
- 优化模块列表的加载状态展示逻辑。
- 引入前端删除后的缓存清理逻辑。

## 验证计划

### 自动化测试 (Automated)
- 运行 `pytest` 确保后端 CRUD 逻辑 100% 通过。
- 编写 or 运行特定脚本确认 `/system-modules/` 接口返回的数据中已不再包含 "Unknown API"。

### 手动验证 (Manual)
1. **状态切换**：将一个服务从 `Active` 设为 `Deprecated`，检查卡片颜色是否变灰，并刷新页面确认持久化。
2. **责任人编辑**：修改负责人名称并提交，确认数据库已更新。
3. **删除功能**：点击垃圾桶图标，确认弹出确认框，点击确认后服务从列表中立刻消失。

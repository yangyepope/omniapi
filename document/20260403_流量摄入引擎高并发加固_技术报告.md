# [2026-04-03 12:08:15] 重要：OmniAPI 流量摄入引擎高并发加固技术报告

## 一、 背景与挑战 (Overview)

在 OmniAPI 流量治理系统的早期压测中，流量采集端点（`/v1/collect`）在处理高并发请求时出现了严重的物理瓶颈：
- **数据一致性丢失**：在 50 并发下，原始流量统计出现近 30% 的丢失。
- **物理死锁 (Deadlocks)**：由于并发线程对 `SystemModule` 和 `ApiEndpoint` 表的竞争顺序不一致，导致数据库事务大规模回滚。
- **架构冗余**：最初采用“读取-修改-回写”的非原子模式，在高频碰撞下无法保证数据对账。

## 二、 核心加固技术方案 (Technical Architecture)

为了彻底解决上述问题，我们实施了 **V8.0 "Prestige" 架构加固计划**：

### 1. 全局严格锁序 (Strict Lock Hierarchy)
**原则**：强制所有并发线程按照物理表层级顺序持锁。
- **路径**：`SystemModule (Parent)` -> `ApiEndpoint (Child)` -> `FilteredFlow (Leaf)`。
- **效果**：从物理层面消除了循环等待，彻底根治了死锁故障。

### 2. PostgreSQL 原子 Upsert
**技术**：利用 `INSERT ... ON CONFLICT DO UPDATE` 指令。
- **实现**：将“检查是否存在”、“创建记录”、“更新计数”合并为单条原子 SQL 指令。
- **优势**：减少了 66% 的数据库往返（Round-trip），将逻辑下沉至数据库引擎层。

### 3. SQLAlchemy 表达式引擎重构 (V8.0)
**优雅化**：放弃原生字符串 SQL，全面迁移至 SQLAlchemy PostgreSQL Core 表达式。
- **原子累加**：通过 `Column + 1` 表达式实现数据库内原子增量，避免脏读。
- **强类型安全**：消除硬编码表名，利用 SQLModel 实现 100% 的字段类型检查。

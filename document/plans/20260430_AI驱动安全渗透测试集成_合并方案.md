## ⚠️ 重大遗留（投产前必须处理）

> 本节为本次落地后**未解决**的硬性遗留，部署到 staging 之前必须有人专门跟进。
> 三项中的任意一项不补齐，整套扫描平台都不能算"可用"。

### 🔴 遗留 1：检测规则全部为空（`agents/*.md` + `rules/*.yaml`）

- **现状**：10 个 `agents/*.md` 仅是 22 行通用占位描述；24 个 `rules/*.yaml` 全部是 `rules: []` 空列表
- **原因**：清理 backend 早期实验性集成（`rm -rf backend/app/services/ai_audit/`）时，连带删除了未提交的 397 条规则。git fsck / 系统回收站均无法恢复
- **影响**：当前 Agent 只能凭 LLM 通用知识审计，**漏报率会非常高**；规则命中率统计失效；规则 ID 全是 `CUSTOM`
- **处理方式**：按 v3.0 §4.1 / §5.2 表格逐文件重写
  - 10 个 agent 角色定义（每个约 50-100 行）
  - 24 个 yaml 共 397 条规则，按下表分布：

  | 规则文件 | 数量 | 规则文件 | 数量 |
  |---------|------|---------|------|
  | sql_injection | 15 | ai_llm_security | 45 |
  | xss | 15 | auth_failures | 42 |
  | ssrf | 12 | broken_access_control | 16 |
  | injection | 12 | cryptographic_failures | 12 |
  | security_misconfiguration | 25 | insecure_design | 17 |
  | logging_failures | 24 | deserialization | 10 |
  | file_security | 19 | information_disclosure | 18 |
  | microservice_security | 10 | protocol_security | 11 |
  | iam_lifecycle | 12 | api_rate_limiting | 12 |
  | third_party_integration | 12 | data_privacy | 12 |
  | event_driven_security | 12 | caching_security | 12 |
  | thread_context_security | 10 | spring_autoconfig_security | 12 |

- **优先级**：🔴 **最高** — 没规则等于扫描平台空跑

### 🔴 遗留 2：Joern CPGQL 脚本只导出基础节点，**Source→Sink 路径未实现**

- **现状**：`joern-runner/scripts/extract_cpg.sc` 仅导出 controllers / methods / calls / sql_sinks，`paths` 字段返回空数组
- **影响**：
  - Activity 5 (call_chain_query) 仅依赖 Neo4j 中已有的 CALLS 关系做 1-6 跳查询，缺乏 Joern 标准的 `reachableBy` 污点流分析
  - "Source→Sink 数据流"（v3.0 §2.2 核心卖点）只能依赖 Python 端的 `call_chain_resolver` + 正则启发式兜底
  - SQL 注入、SSRF、XSS 等需要追踪用户输入流到危险函数的检测**精度大幅下降**
- **处理方式**：补充 CPGQL 跨函数 `reachableBy` 查询，例如：
  ```scala
  val sources = cpg.parameter.where(_.method.annotation.name(
    "RequestParam","RequestBody","PathVariable"))
  val sinks = cpg.call.name("executeQuery","createNativeQuery", ...)
  val flows = sinks.reachableByFlows(sources)
  ```
  把 flows 序列化到 JSON 输出 `paths` 数组
- **优先级**：🔴 **高** — 影响检测能力上限

### 🟡 遗留 3：端到端启动测试未做

- **现状**：本环境受限未拉 Joern 镜像（约 1.5 GB）；Neo4j / Temporal 容器未启动；Webhook 未经 GitLab 联调
- **未验证项**：
  - `joern-parse` 在容器内能否正常工作（环境变量、JVM 堆、文件权限）
  - `extract_cpg.sc` 在真实 Java 项目上是否报错
  - Neo4j 5.20 + APOC 启动是否正常
  - Temporal Schedule 注册时机（worker 启动顺序、auto-setup 镜像首次初始化）
  - GitLab Webhook 连通性（X-Gitlab-Token 校验路径）
  - Backend `INTERNAL_API_TOKEN` 与 aisec `TRAFFIC_PLATFORM_TOKEN` 双向匹配
  - 8 Activity 的实际耗时与超时值是否合理
- **处理方式**：按本文 §13 "验收标准" 清单逐步执行；第一次跑会暴露镜像版本、网络、配置等问题
- **优先级**：🟡 **中** — 部署到 staging 第一天必做

## 一、最终架构形态

经讨论后**确认采用顶层独立项目方案**（与 v1.0 草案中"作为 security-platform 子模块"路线相比）：

```
security-platform/
├── frontend/                  # 既有
├── backend/                   # 既有，仅加一条 internal 路由作为回传出口
├── aisec/                  ★ 新增独立项目（Python 包名 aisec）
├── joern-runner/              ★ 新增独立组件（Joern CLI 的 HTTP 包装）
├── document/                  # 方案文档（本文件）
└── compose.yml                # 编排所有平级服务
```

**这样组织的理由：**
- 职责清晰：扫描平台 ≠ 主业务，进程级隔离
- 依赖隔离：`anthropic` / `pydantic-ai` / `neo4j` / `temporalio` 等不污染 backend `pyproject.toml`
- 部署独立：升级 Joern / Claude 模型不需要重启主链路
- 目录树严格对齐 v3.0 §5
- 后续抽出去开源 / 复用零摩擦

## 四、Workflow 编排（实际落地为 10 Activity）

```
ScanWorkflow（v3.0 §3.2）

A1  resolve_source_plan              ← GitLab 元数据 + 模块识别
A2  sync_source_files                ← 按 service+commit 增量下载（heartbeat）
A3  build_cpg                        ← Joern + resolver + 兜底（heartbeat，最长）
A4  store_cpg                        ← Neo4j 持久化
A5  discover_interfaces              ← 按服务查 Controller
A6  query_call_chains                ← Neo4j Source→Sink 查询
    ├ persist_agent_results          ← 辅助：joern_path 落库
A7  run_agents                       ← 10 Claude Agent 并发（heartbeat）
A8  summarize_findings               ← Claude 攻击链推断 + 严格 ScanSummary
A9  publish_results                  ← PG save + HTTP 回传 + 通知

辅助 Activity：
    _fetch_scan_run_id               ← Workflow 内取 PG ID
    _fetch_joern_path_lookup         ← 反查 joern_path 关联表

异常路径：
    mark_scan_failed                 ← Workflow except 捕获 → PG 标 failed
```

**每个 Activity 单独配置超时 + 重试**（v3.0 §3.3）：

| Activity | 超时（min） | 重试 | 心跳 |
|---------|-----------|-----|------|
| resolve_source_plan | 10 | 3 | — |
| sync_source_files | 10 | 3 | 60s |
| build_cpg | 60 | 1 | 5min |
| store_cpg | 15 | 3 | — |
| discover_interfaces | 5 | 3 | — |
| query_call_chains | 5 | 3 | — |
| run_agents | 30 | 2 | 5min |
| summarize_findings | 10 | 2 | — |
| publish_results | 5 | 3 | — |

### Workflow ID 规则（v3.0 §3.5）

| 触发类型 | Workflow ID |
|---------|-------------|
| MR | `scan-{project_id}-mr-{mr_iid}` |
| push | `scan-{project_id}-push-{commit_short}` |
| 定时 / 手动 | `scan-{project_id}-scheduled-{YYYYMMDDHHMM}` |

webhook 启动 Workflow 前先 `cancel_existing_workflow(client, wf_id)`，
若同 ID 在 Running 则发送 Cancel Signal，再启动新 Workflow。

### 5.2 security-platform 主库（仅复用，不新建表）

每条 finding 通过 HTTP 推送到 `backend` 后，由 `routes/internal.py` 落到：
- **flow_tags**：tag = `"{rule_id}:{severity}"`
- **variants**：source_type=`'scan'`, origin=`'aisec/{scan_id}'`（仅当 payload_hint 非空）

→ 用户在流量采集平台界面打开任一 FilteredFlow 即可看到该接口的扫描标签和派生变体。

## 八、Temporal Schedule 定时

启动 worker 时 `register_schedules(client)` 自动注册：

- 对 `SCHEDULED_SCAN_PROJECTS` 中每个 project_id 创建 `scheduled-{project_id}` schedule
- cron 由 `SCHEDULED_SCAN_CRON`（默认 `0 2 * * *`）控制
- 每次触发产生 mode=full 的 ScanWorkflow

幂等：已存在的 schedule 不会重建。

---

## 九、通知

`notify_scan_completed(scan_id, summary)` 在 publish_results Activity 末尾调用：

- 当 summary 中存在 ≥ `NOTIFY_MIN_SEVERITY`（默认 HIGH）的发现才推送
- 同时支持飞书 / 钉钉 / 邮件三种渠道
- 单一渠道失败不阻塞其他

## 十三、验收标准

部署后通过下列步骤完成端到端验收：

```bash
# 1. 准备配置
cp aisec/.env.example aisec/.env
# 在 security-platform/.env 中也加：INTERNAL_API_TOKEN=<同 TRAFFIC_PLATFORM_TOKEN>

# 2. 拉起依赖（首次）
docker compose up -d db redis temporal neo4j joern-runner
docker compose run --rm aisec-prestart

# 3. 拉起服务
docker compose up -d aisec-api aisec-worker backend

# 4. 健康检查
curl http://aisec/health
curl http://joern-runner:8090/health

# 5. 手动触发一次扫描
curl -X POST http://aisec/api/scan/full \
  -H "Content-Type: application/json" \
  -d '{"project_id": <你的 GitLab project_id>, "git_ref": "main"}'

# 6. 在 Temporal UI 看 Workflow 执行
# 7. 在 GET /api/scans/{scan_id}/findings 查结果
# 8. 登录 security-platform 流量采集平台 UI，查看对应 endpoint 的 FlowTag / Variant
```

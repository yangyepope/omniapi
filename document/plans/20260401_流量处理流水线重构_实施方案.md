# 实施方案 - 流量处理流水线重构 (V1.0)

本项目旨在重构后端的流量捕获与处理逻辑，实现一套包含原始存储、异步去重、服务发现的三阶段高性能流水线。

## 需用户核对 (User Review Required)

> [!IMPORTANT]
> - **数据库迁移**: 此次变更涉及 `RawFlow` 和 `FilteredFlow` 的字段调整。我们将使用 SQLModel/SQLAlchemy 进行定义。如果表中已有测试数据，建议在执行前清理，以确保存储结构的一致性。
> - **TTL (自动清理) 策略**: `RawFlow` 的 3-7 天自动清理将通过 Celery 定期任务 (Periodic Task) 实现，或者在每次摄入时检查过期时间。

## 提议变更 (Proposed Changes)

### 1. 数据库模型对齐
#### [修改] [models.py](file:///root/omniapi/backend/app/models.py)
- **RawFlow (原始流量表)**:
    - 确保 `captured_at` 具有毫秒级精度的 UTC 时间。
    - 增加/更新 `service_name` 字段，用于存储从 URL 第一层提取的服务名。
    - 确保 `headers` (JSONB) 和 `body` (LargeBinary/Text) 结构符合存储规范。
    - 增加 `dedup_key` (MD5) 占位符及 `status` 状态字段。
- **FilteredFlow (精选流量表)**:
    - 确保与 `ApiEndpoint` 建立永久链接。
    - 存储清洗后的 Header（排除敏感/动态字段）和精简 Body。

### 2. 流量捕获入口重构
#### [修改] [collect.py](file:///root/omniapi/backend/app/api/routes/collect.py)
- 更新 `collect_traffic` 逻辑：
    1. **服务名提取**: 从 `original_uri` 的首层路径提取（例如 `/sts/list` -> `sts`）。
    2. **即时存库**: 将请求完整信息写入 `RawFlow` 表。
    3. **异步触发**: 调用 Celery 任务 `process_raw_flow_task(raw_flow_id)`。

### 3. 异步处理与去重逻辑
#### [修改] [worker.py](file:///root/omniapi/backend/app/worker.py)
- 实现 `process_raw_flow_task`:
    - **Header 过滤**: 排除 `Date`, `X-Timestamp`, `Cookie`, `Authorization` 等字段。
    - **Body 过滤**: 排除 `timestamp`, `nonce`, `sign` 等全局配置的动态字段。
    - **MD5 计算**: 将 (服务名 + 归一化路径 + 方法 + 过滤后的 Header + 过滤后的 Body) 组合并计算哈希。
    - **幂等检查**: 如果该 `dedup_key` 已存在于 `FilteredFlow` 中，则标记原始记录为重复并跳过。
    - **服务发现**: 如果是新特征报文，创建/关联 `FilteredFlow` 并触发接口路径归一化匹配。

### 4. 服务发现与归一化
#### [修改] [discovery.py](file:///root/omniapi/backend/app/services/discovery.py)
- 强化 `normalize_uri`: 确保剥离 Query 参数，并将 `/users/123` 准确识别为 `/users/{id}`。
- 增加辅助函数 `extract_service_name_from_path`。

### 5. 前端逻辑配合
#### [修改] [business-config/index.tsx](file:///root/omniapi/frontend/src/routes/_layout/business-config/index.tsx)
- 确保资产中心展示的是经过“归一化”和“去重”后的精品数据。

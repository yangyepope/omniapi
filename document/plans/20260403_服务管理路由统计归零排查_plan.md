# 服务管理路由统计归零排查计划（/plan）

## 1. 需求摘要

- 现象：服务管理「接口管理」页面显示已采集 3 条流量，但归一化路径行内的流量统计均为 0。
- 目标：先排查并复现根因，不直接修改生产逻辑；执行 `/plan` 与 `/tdd` 流程后，再给出最小修复方案待确认。

## 2. 技术方案

- 方案 A（推荐）：基于 `FilteredFlow` 做真实对账，校验 `ApiEndpoint.total_traffic_count` 与 `count(filtered_flows)` 一致性。
- 方案 B（排除）：仅看 `variant_count` 汇总。该字段用于“重复命中增量”，不等价于总流量，不能作为总流量来源。

决策：
- 以 `count(filtered_flows)` 为 endpoint 总流量事实来源。
- 以 `count(filtered_flows)` 为 endpoint 唯一样本数（`variants_count`）。
- 模块级总流量以 endpoint 聚合或 worker 原子计数维持。

## 3. 实施阶段

### 阶段一：只读定位（已执行）

- 目标：确认是否存在“有流量记录但 endpoint 计数为 0”的数据漂移。
- 涉及文件：

  - `backend/tests/scripts/sync_traffic_stats_hotfix.py`
  - `backend/app/services/discovery.py`
- 完成标准：
  - 在本地查询中复现 mismatch。
  - 复现样本包含用户报告的 `config` 三条路径。

### 阶段二：TDD 红灯用例（进行中）

- 目标：先新增失败测试，精确描述 bug 行为，不改生产代码。

- 完成标准：
  - 测试能在当前实现下稳定失败。
  - 失败信息指向“总流量不能由 `sum(variant_count)` 推导”。

### 阶段三：最小修复实现（待确认）

## 4. 风险评估

- 风险 1：历史数据中 `variant_count` 语义被误用为总流量来源。
  - 缓解：明确口径为 `count(filtered_flows)`，并补充一致性测试。
- 风险 2：并发处理与回填脚本口径不一致导致再次漂移。
  - 缓解：脚本与 worker 计数语义对齐，增加脚本级断言。
- 风险 3：只修 endpoint 不修 module 造成上层统计偏差。
  - 缓解：补充模块级聚合复核。

## 5. 测试策略

- 单元/功能测试：
  - 新增“endpoint 计数一致性”失败用例（RED）。
  - 修复后同用例转绿（GREEN）。
- 数据对账验证：
  - 抽样核对 `apiendpoint.total_traffic_count` vs `count(filtered_flows)`。
- 回归验证：
  - 服务管理页面中目标路径统计值与对账结果一致。

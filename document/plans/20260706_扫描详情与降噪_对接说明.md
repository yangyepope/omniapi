## 一、scanner(数据源)契约变更 —— 平台要消费的

scanner 已重建部署(容器 `gitlab-scanner`),以下对平台可见:

1. **scan run 新状态值 `timed_out`**(FEAT-010):进程死亡卡 `running` 的运行,被后台 sweeper 收敛为 `timed_out`。前端 `ScanRun.status` 枚举、`SCAN_STATUS_META` 需含此值(**本仓库已加**)。

2. **新接口 `GET /api/admin/services/{name}/scan-runs/{run_id}`**(FEAT-011)→ `ScanRunDetail`:
   - 继承列表项全部字段 + `current_stage`(正在执行阶段)、`last_heartbeat`、`seconds_since_heartbeat`(存活)、`findings_count`、`by_engine[]`(逐引擎:engine/status/elapsed_seconds/findings/tokens/model)。
   - `phases_completed` 阶段完成时间戳。
   - 404:run_id 不属于该 service。

3. **scan-runs 列表项加性新增** `current_stage` / `last_heartbeat`(FEAT-011)。

4. **finding 可能出现新裁决值 `needs_review`**(FIX-008):复核 LLM 失败时写此标记(finding 仍 open)。前端裁决渲染不要因未知值报错(它本就在 `VerdictLiteral` 里)。

5. **行为变化**:scanner 复核默认开启(`AI_FINDING_REVIEW_ENABLED=True`)→ semgrep/spotbugs/codeql 的误报会被判 `ai_false_positive` 并关闭 → 平台 findings 列表噪音显著下降;风险分级逻辑变更时旧分级自动重判(`CLASSIFY_VERSION`)。**平台侧无需改动,自然受益。**

> 平台侧**无新增环境变量**,`SCANNER_BASE_URL` / `SCANNER_ADMIN_TOKEN` 不变;平台不落库(纯代理)。

## 五、追加:源码缓存管理(gitlab-scanner FEAT-012 / 本仓库 FEAT-005)

**scanner 新接口(平台已代理):**
- `GET /api/admin/services/{name}/source-cache` → `list[SourceCacheItem]`(sha/ready/pulled_at/size_bytes/is_last_scanned)。
- `DELETE /api/admin/services/{name}/source-cache/{sha}` → 逐出缓存 + 清该 sha 续跑标记(ai_plan_runs/interface_risk_runs/scan_runs),**保留 findings**。

**本仓库已改(待 review+提交+部署):**
- 后端:`scanner_client.list_source_cache/evict_source_cache` + `/security/services/{name}/source-cache[/{sha}]`(DELETE 挡 inactive)。
- 前端:`api.ts`(SourceCacheEntry + 方法)、`hooks.useSourceCache`、服务详情新增「源码缓存」tab(列表 + 删除/删除并重扫)。

**运维前提(重要):** 删除缓存后"重拉"需 scanner 配 **`GITLAB_ACCESS_TOKEN`** 才能解析 project_id;当前为空,删掉的 sha 无法重拉(archive 404)。要用"删除并重扫"必须先配 token。

**行动项(并入上面第三节):** review + 提交 + 前端重建 + 后端重部署;回归:源码缓存 tab 列出/删除、findings 不受影响。

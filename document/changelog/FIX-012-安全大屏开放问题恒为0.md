# FIX-012 安全大屏「开放问题」恒为 0

- **编号**: FIX-012

- **状态**: 已完成

- **关联 PR·Issue**: 无

## 需求背景

安全大屏「开放问题」KPI 恒显示 `0`,但同屏「严重问题(仅 CRITICAL)」= 93、「覆盖服务数」= 11 都有值,明显矛盾——有开放的严重问题却说开放数为 0。用户反馈"这两个指标都是 0,有问题"。

同时被质疑的「AI 误报抑制率 = 0.0%」经核查**不是 bug**(详见验证方式),本 FIX 只修「开放问题」。

## 技术实现

### 根因

前端 [SecurityDashboard.tsx](../../frontend/src/security/SecurityDashboard.tsx) 读的是 `stats.data?.open_findings`,而 scanner `/api/admin/stats` 的响应体 `StatsResponse`(gitlab-scanner `app/api/routes/admin.py`)**从来不返回 `open_findings` 字段**,只返回 `total_findings / by_severity / by_engine / by_status / services_count / last_scan_at`。

前端手写的 `Stats` 类型([security/api.ts](../../frontend/src/security/api.ts))凭空声明了 `open_findings: number`,平台后端 `get_stats` 又以 `dict[str, Any]` 原样透传(无 schema 校验),于是:
- TS 编译期检测不到字段缺失(手写类型撒了谎);
- 运行期 `stats.data.open_findings` 恒为 `undefined` → `?? 0` 静默兜底成 `0`。

真实开放数其实就在响应的 `by_status.open` 里(finding.status 默认 `"open"`,取值仅 `open|closed`)。

### 修改

- `SecurityDashboard.tsx`:`open` 改读 `stats.data?.by_status?.open ?? 0`,加注释说明取数口径。
- `security/api.ts`:删除 `Stats` 类型里不存在的 `open_findings` 字段(消除前端与 scanner 契约的双轨)。

无后端/迁移/DB 改动。

## 验证方式

- [x] tsc 类型检查通过(`npx tsc --noEmit`,无孤儿引用)
- [x] 实打 scanner 线上 `/api/admin/stats`:`by_status = {"closed": 27, "open": 1013}`、`total_findings = 1040`、响应**无** `open_findings` 键——证实真实开放数应为 1013,原先显示 0 是读错字段
- [x] 「AI 误报抑制率 = 0.0%」定性为**非 bug**:实打 `/api/admin/verifier-stats` 得 `total_ai_findings=146, no_verifier=0, confirmed=141, refuted_high=0, refuted_medium=0, refuted_low=5`;verifier 已全跑(no_verifier=0),仅以 low 置信度驳回 5 条,而抑制率公式只计 `(high+medium)/verified_total`,故 `0/146 = 0.0%` 如实反映 verifier 弱驳回现状

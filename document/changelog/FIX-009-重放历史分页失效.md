# Bugfix 归档：重放历史记录分页失效故障 (2026-04-06)

## 1. 故障现象
*   **用户观测**：在执行 1000 次极限压测后，变体详情页的“重放历史”选项卡仅显示 5 页（共 50 条）记录，无法查看后续的 950+ 条压测流水。
*   **物理状态**：数据库 `replay_results` 表中实际存在 1003 条记录，原子计数 `replay_count` 准确（1003）。

## 2. 根因分析
该故障由 **“前后端脱节的假分页”** 导致：
1.  **后端响应缺失**：`/api/v1/variants/history` 接口在返回数据时，未包含 `count` 字段。且由于 SQLModel 默认未处理分页，导致仅返回了前 50 条记录。
2.  **前端逻辑错误 (`HistoryTimeline.tsx`)**：组件采用了 **“客户端分页 (`.slice()`)”**。它假设 Props 传入的数组就是全量数据。由于后端只给了 50 条，组件便误判总共有 `Math.ceil(50/10) = 5` 页。

## 3. 修复措施
### 3.1 后端修复 (`variants.py`)
*   引入 `count_statement` 物理计数字段。
*   修正 API 契约，返回格式改为 `{"data": [...], "count": 1003}`。
*   显式支持 `skip` 和 `limit` 参数以支撑服务端分页。

### 3.2 前端修复 (`index.tsx` & `HistoryTimeline.tsx`)
*   **父组件升级**：引入 `historyPage` 状态，将分页请求从客户端拦截改为服务端透传。
*   **子组件重构**：废弃本地 `.slice()` 逻辑。升级 `Props` 以接收外部传入的 `totalCount` 和 `currentPage`，并通过 `onPageChange` 回调触发翻页请求。

## 4. 验证结论
*   **UI 表现**：页面底部显示“显示第 1 到 10 条结果，共 1003 条”，分页器正确延伸至 101 页。
*   **性能提升**：不再一次性加载 1000+ 条 DOM，仅按需加载当前页，内存占用降低 90% 以上。

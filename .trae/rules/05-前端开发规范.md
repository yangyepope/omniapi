# SecurityPlatform 前端开发规范与架构指南

## 一、 技术栈锁定 (Tech Stack)
*   **核心框架**：React 19 + Vite 7。严禁使用已废弃的 React API（如类组件），全面拥抱 Server Components（若未来引入）和 Hooks。
*   **路由管理**：强类型路由 **TanStack Router**。所有页面路由必须基于文件系统自动生成，严格利用路由参数的类型推导。
*   **语言与样式**：严格的 **TypeScript** + **Tailwind CSS v4**。禁止手写常规的 `.css` 文件，特殊样式优先使用 Tailwind 任意值语法（Arbitrary values）。
*   **工程化工具**：使用 **Biome** 进行代码格式化和 Linting（`bun run lint`），测试采用 **Playwright**（`bun run test`）。

## 二、 组件与 UI 规范 (Component & UI Rules)
*   **原子化组件库 (shadcn/ui 优先)**：
    *   强制要求优先使用 `shadcn/ui` 组件库（基于 Radix UI）。
    *   当需要新基础组件时，必须先检查 `@/components/ui` 是否已有。如果没有，应通过 CLI 引入，**严禁从零手写基础弹窗、下拉菜单等复杂交互组件**。
    *   类名合并必须使用已封装好的 `cn()` 工具函数（基于 `clsx` 和 `tailwind-merge`）。
*   **组件单一职责 (Single Responsibility)**：每一个生成的组件文件必须保持精简，**不得超过 150 行**。如果逻辑过于复杂，强制要求进行拆分。
*   **Client/Server 声明 (RSC 预留)**：虽然当前采用 Vite 7，但若代码或后续架构中引入 React Server Components，**强制要求** AI 明确区分 `'use client'` 和 Server Components。
*   **Tailwind 排序**：强制遵循标准的 Tailwind 类名排序（本项目中通过 Biome 实现，等同于 `prettier-plugin-tailwindcss` 规则），让 AI 生成的类名易于维护和阅读。
*   **图标规范**：统一使用 `lucide-react`，严禁引入其他图标库导致包体积膨胀。
*   **响应式设计 (Mobile-First)**：
    *   所有页面必须支持移动端适配。
    *   默认样式为移动端（小屏幕），大屏适配严格使用 Tailwind 的断点前缀：`sm:` (640px), `md:` (768px), `lg:` (1024px), `xl:` (1280px)。
*   **主题管理**：暗黑模式切换依赖 `next-themes`，所有自定义颜色必须使用 CSS 变量（如 `bg-background`, `text-foreground`）以支持主题无缝切换。

## 三、 状态管理与数据获取 (State & Data Fetching)
*   **异步数据 (Server State)**：
    *   **绝对禁止**在 `useEffect` 里手动使用 `fetch` 或 `axios` 获取数据。
    *   所有的 API 请求、缓存、同步、重试状态，必须交由 **TanStack Query (React Query)** 管理（使用 `useQuery`, `useMutation` 等）。
*   **同步状态 (Client State)**：
    *   优先使用局部状态 `useState` / `useReducer`。
    *   涉及到 URL 可分享的查询参数（如分页、搜索关键词），必须存储在 TanStack Router 的 `search` params 中，实现 URL 驱动状态。

## 四、 前后端契约与 API 交互 (Contract-First API)
*   **API 客户端自动生成**：
    *   严禁手动编写 API 调用层！项目已配置 `@hey-api/openapi-ts`。
    *   开发流程：后端更新 FastAPI Pydantic/OpenAPI schema -> 运行 `bun run generate-client` -> 前端直接调用生成的 Service 方法。
*   **类型绝对安全**：
    *   不准在前端手动定义后端的返回数据 Interface。必须导入由 `openapi-ts` 自动生成的类型定义。
    *   字段命名严格遵从生成的类型，无需前端手动进行 `snake_case` 到 `camelCase` 的转换（生成器已处理或保持契约一致）。

## 五、 表单与校验 (Forms & Validation)
*   **表单状态管理**：复杂表单必须使用 `react-hook-form` 统一管理，禁止使用大量独立的 `useState` 来绑定表单字段。
*   **Schema 校验**：
    *   强制使用 `zod` 定义表单的数据结构和校验规则。
    *   结合 `@hookform/resolvers/zod` 将校验规则注入到 `react-hook-form` 中，实现类型推导与错误拦截的双重安全。

## 六、 错误处理与用户提示 (Error Handling & Feedback)
*   **全局提示 (Toast)**：
    *   项目已集成 `sonner`。所有的增删改查（Mutation）操作后，必须通过 `toast.success()` 或 `toast.error()` 给予用户明确的反馈。
*   **API 错误拦截**：
    *   API 层的调用必须妥善处理异常。在 `useMutation` 的 `onError` 回调中，必须解析后端的错误信息（如 FastAPI 返回的 `detail` 字段）并展示给用户。
*   **渲染错误边界**：
    *   可能引发崩溃的复杂组件树，必须包裹在 `react-error-boundary` 中，提供优雅的降级 UI (Fallback)，防止整个 SPA 白屏。

## 七、 目录结构约定 (Directory Structure)
*   `/src/routes`：放置 TanStack Router 的文件路由定义与页面级组件。
*   `/src/components/ui`：放置 shadcn/ui 的原子化基础组件。
*   `/src/components/common` 或 `/src/features`：放置业务相关的复合组件。
*   `/src/client` 或 `/src/api`：放置 `openapi-ts` 自动生成的 API 代码（请勿手动修改该目录下内容）。

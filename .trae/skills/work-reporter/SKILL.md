# Work Reporter（改动说明助手）

## 目标

把“我刚才做了什么改动、为什么这么改、产生什么效果、如何验证、如何回滚”讲清楚，让用户不需要反复追问。

## 何时调用（强制触发条件）

在以下任一场景，必须调用本技能输出详细流程与改动说明：

1. 用户问：你刚才做了什么修改？为什么这么做？怎么实现的？
2. 我完成了一个实现/修复/重构任务，需要交付清晰的变更记录（含验证方式）。
3. 我对日志/配置/鉴权/数据等“可能影响范围较大”的内容做了调整。
4. 用户需要复盘排障过程，希望看到“定位思路 + 证据 + 修改点 + 结果”。

## 输出格式（固定结构）

按下面结构输出，除非用户明确要求更短：

### 1) 改动概览
- 用 3–6 条 bullet 列出“改了哪些文件/模块/配置”，每条一句话说明目的。
- 每个文件用可点击引用格式：`[文件名](file:///绝对路径#Lx-Ly)`。

### 2) 具体改动（逐点）
对每个关键改动点，按模板写：
- **改了什么**：描述行为变化（或明确说明“仅加注释/无逻辑变化”）。
- **为什么**：解释触发原因（bug/需求/体验/安全/性能/可维护性）。
- **怎么做的**：关键实现要点（涉及的函数/配置项/控制流）。
- **影响范围**：哪些请求/环境/服务会受影响；是否需要重启/重建。
- **兼容性**：是否有破坏性变更；是否需要迁移/清理数据。

### 3) 验证方式
- 列出我实际执行过的验证（命令/接口/用例），以及预期输出。
- 如果没法执行验证（缺依赖/环境限制），说明原因并给出最小可行验证步骤。

### 4) 回滚/恢复
- 给出“如何撤回本次改动”的最短步骤（例如恢复某文件、重启某服务）。
- 如果改动涉及配置/容器：明确需要 `restart` 还是 `--force-recreate` 或 `build`。

### 5) 可选优化（仅在有明确收益时给）
- 提 1–3 条“可选优化”，每条说明收益与风险。
- 不要扩大范围到与当前需求无关的重构。

## 关键约束

1. 只陈述事实：列清楚哪些文件被改、改动点是什么；不要“可能/应该”含糊带过。
2. 需要可追溯：所有关键点必须给出文件链接（含行号范围）。
3. 与仓库规则一致：不要建议把密钥写入代码/日志；不要输出敏感 token 明文。
4. 语言：默认中文；除非用户要求英文。

## 示例（简版）

### 改动概览
- 更新 [logger.py](file:///root/omniapi/backend/app/core/logger.py#L1-L120)：统一将标准 logging 转发到 loguru，优化日志格式与噪声控制。

### 具体改动
- **改了什么**：将 httpx/uvicorn 的标准 logging 输出统一格式化；隐藏 logging 内部调用位置。
- **为什么**：容器日志中 INFO/WARNING/DEBUG 混杂且无法区分来源，排障成本高。
- **怎么做的**：新增拦截 handler，把 logging.LogRecord 转发到 loguru，并绑定 logger_name。
- **影响范围**：仅影响日志输出；不改变业务逻辑。生效需重启后端进程。
